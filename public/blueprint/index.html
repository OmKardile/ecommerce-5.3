Section 1

What this system is

A single web application with three faces: a public storefront for buyers, a self-service account area for customers, and a permission-scoped operations console for the shop team. One Next.js codebase, one database, one deployment.

Storefront (public)

Catalog, filters, product pages, CCTV kit builder, cart, checkout with GST invoices, order tracking, blog and policy pages. Customers log in with an OTP to their phone — no passwords to forget.

Customer account

Order history, live tracking timeline, printable GST invoices, address book, wishlist with price-drop tracking, B2B profile (GSTIN) for input tax credit.

Operations console

The /admin panel: orders & fulfillment, inventory & stock monitor, catalog management, customers, marketing content, reports, settings — each section granted per staff account by the Owner.

Three rules baked into the design

  • 1 · Money is never a decimal.
    Every amount is stored as an integer of paise (₹1,450.00 = 145000). Rounding errors are impossible; GST splits (CGST/SGST vs IGST) are computed server-side.
  • 2 · Stock only exists at the SKU.
    Every physical unit is one SKU row; every change to stock is appended to an immutable inventory_movements ledger with a reason code. Stock can always be reconstructed and audited.
  • 3 · Staff never touch stock directly.
    The stock monitor is observe-and-report: employees propose corrections, a manager approves, and only then a real movement is written (two-man rule, fully audited).

The catalog spine — how one camera reaches a customer

Follow the brass boxes left to right. This is the single most important chain in the database.

categories＋ brands→ products→ product_images · product_variants→ skus→ inventory→ inventory_movements
ONE SKU FEEDS ↓ cart_items order_items bundle_items stock_alerts stock_count_lines adjustment_requests

A Product is the brochure ("2MP Dome Camera"); a Variant is one combination of attributes (2MP · 3.6mm lens); a SKU is the warehouse item with a price and stock count. Orders snapshot SKU data at purchase time, so editing the catalog later never rewrites history.

How a permission is checked — every single request

Request + session cookie→ Route guard (/admin)→ API validates input (Zod)→ Re-reads user row from DB — fresh→ Scope granted? → run Not granted → 401

Because gates re-read the database each time (not a cached token), the moment the Owner edits a staff member's scopes or deactivates them, it bites on that person's very next click — no logout needed. Every grant/revoke lands in the audit log.

Staff creation wizard — the 3 steps

  1. Identity — name, email, auto-generated password (shown once, copyable).
  2. Functions — account type (Staff or second Owner), then tick exactly which of the 15 functions this person gets. Quick presets: Counter, Warehouse, Fulfillment, Catalog, Content.
  3. Review & create — confirm; the account is live immediately and scoped to the ticked functions only.

Editing later: the Owner can rename, reset passwords, change scopes, or deactivate — all audited. A staff member with zero scopes sees an empty console, never another department's data.

Section 5

Order lifecycle — 13 states, strictly enforced

The server allows only the transitions drawn below (a finite state machine). Customer tracking, staff pipeline, and the ledger all read from this single truth.

A Checkout & payment

PENDING_PAYMENT→ PAID→ CONFIRMED COD_PENDING→ CONFIRMED

Stock is reserved the moment the order is created (available = current − reserved). Razorpay payments are signature-verified and replay-safe; COD follows the selective-COD rules (per-product flag, ₹15,000 ceiling, air-cargo zones blocked). B2B buyers add GSTIN for input tax credit.

B Fulfillment

CONFIRMED→ PROCESSING→ PACKED→ SHIPPED→ OUT_FOR_DELIVERY→ DELIVERED

At PACKED: hardware serial numbers captured (warranty/RMA keys) and AWB generated. At SHIPPED: physical stock decrements via an ORDER_DISPATCHED movement; courier events stream into shipment_events and the customer timeline.

C After-sales

DELIVERED→ RETURN_REQUESTED→ RETURNED→ REFUNDED CANCELLED possible from any pre-dispatch state

Returns (and DOA/RMA claims) restock units via RETURN_RESTOCK movements; refunds flip the payment record. Cancelling before dispatch releases the reservation — nothing is ever double-counted.
